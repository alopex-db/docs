# v0.8.17 SQLite複合SQL固定比較

複合SQLの実行時間は、修正前に対して元の操作列で20.10%、制約検査付きで19.60%短縮した。公開v0.8.16との比較でも改善条件を満たした。ただし、制約検査付きのSQLite比は15.7026倍で参照目標に未達であり、RSSも増えている。改善の採用条件と残る資源増加を別々に評価する。

[run 42444773094](https://github.com/alopex-db/alopex/actions/runs/42444773094)の24セル、実行504標本と計画504標本を収録した。warmup込み1,152観測区間について、資産・導入実体、全値、rollback後の状態、CPU・RSS・I/O、全workerの終了と回収を独立照合している。

## 元の操作列と制約検査付きの操作列を分けた

両系統とも、COUNT、ORDER BY LIMIT 16、transaction内のINSERT・savepoint・UPDATE・rollback、prepared query、制約付きINSERTとrollbackを実行した。SQLiteの元系統はforeign_keys=0を保持し、検査系統では1に設定した。元系統は過去の比較境界を保存するための値であり、外部キーの責務が揃った性能比較には検査系統を用いる。

検査系統は実際のSELECT返却値について型・列順・行順・全値を毎標本で検証する。外部キー違反とCHECK違反の拒否、savepointで戻る値と残るINSERTも計時外で確認した。元系統は返却値を破棄する元の操作列を維持し、各標本後の全fixtureとrollback後の状態、ケース前後のSELECT結果を照合した。

入力は元の34,250行。同じ管理VMで、4対象を各系統3試行、セルごとに別プロセスで逐次実行した。各区間は3 warmups・21 samplesで、対象順を系統・試行ごとに交替した。embeddedのmemory DBを使い、fixture準備と状態検証を計時外に置いた。CPU割当とthread設定1を固定し、実行時のaffinityを照合した。実機情報と割当の実値は非公開設定に保持する。

## 複合操作は両系統で改善条件を満たした

各試行の21標本中央値を求め、3試行の中央値で比較した。比率は候補/比較対象で、小さいほど速い。ノイズ幅は試行中央値のMADについて両対象の大きい方の3倍とする。baseline中央値の5%を超えれば保留、範囲内で時間比が1.05を超えれば退行と判定した。改善の採用には5%以上の短縮、差がノイズ幅を超えること、3組すべてで改善することを要求している。

| 系統 | 修正前 ms | 候補 ms | 候補/修正前 | 候補/公開版 | 候補/SQLite |
| --- | ---: | ---: | ---: | ---: | ---: |
| 元の操作列 | 20.889182 | 16.691388 | 0.7990 | 0.8258 | 15.9025 |
| 制約検査付き | 20.832854 | 16.750454 | 0.8040 | 0.8132 | 15.7026 |

公開版比の短縮は元系統17.42%、検査系統18.68%。いずれも公開版・修正前に対する改善条件を満たした。SQLiteとの比較は目標未達であり、SQLite中央値を基準にしたノイズ幅も元系統49.57%、検査系統37.74%で基準を超えている。速いbaselineを分母にするため、Alopex側の試行差も大きな割合になる。参照比を合格へ読み替えない。

過去の別実行にある9.551倍と今回の15倍台を直接比較し、退行率とすることはできない。前後比較は本実行内の固定資産・同じ系統・同じ条件で判定する。

## 計画生成の小幅増加とRSS増加は残る

| 系統 | 修正前の計画生成 µs | 候補 µs | 候補/修正前 | 判定 |
| --- | ---: | ---: | ---: | --- |
| 元の操作列 | 106.409 | 105.895 | 0.9952 | 既定条件内 |
| 制約検査付き | 105.545 | 106.707 | 1.0110 | 既定条件内 |

検査系統の計画生成は1.162 µs、1.10%増えた。5%の許容内だが、3 MADの0.693 µsを超える増加として保持する。AlopexはEXPLAIN JSON、SQLiteはEXPLAIN QUERY PLANを取得し、返却形式が異なる。再計算JSONには各値を残すが、計画生成の製品間比率を同じ責務の性能目標には使わない。

| 系統 / 区間 | 修正前RSS bytes | 候補RSS bytes | 増減 |
| --- | ---: | ---: | ---: |
| original-execute | 81,592,320 | 84,811,776 | +3.95% |
| checked-execute | 80,486,400 | 84,529,152 | +5.02% |
| original-plan | 61,775,872 | 72,826,880 | +17.89% |
| checked-plan | 61,714,432 | 72,777,728 | +17.93% |

RSSは各区間のkernel high-water観測値を標本内、試行間で集約した値で、DBやimport済みmoduleを含むworker全体の使用量である。計画区間の約17.9%増加を含めて保持する。計画操作そのものがこの量を追加割当したと断定はできず、fixture準備後の常駐量と処理区間の変化を分けて評価する必要がある。

既存rawの修正前・候補、両系統の計画252標本では、各標本の開始時と終了時のRSSがすべて同じだった。増加分は計測標本の開始時点で存在している。候補の計画区間RSSは第1試行で約65 MB、第2・3試行で約73 MBと分かれる。計測したEXPLAIN中のRSS増加は観測されておらず、準備・事前検証・warmupまでの経路と試行差を次の調査対象にする。この観測は区間内の一時的な割当がないことまでは証明しない。

実行区間のCPU中央値は元系統20.905→16.703 ms、検査系統20.846→16.763 msだった。資源観測区間にはcounter読取りの一部が入り、latencyとは別の指標として扱う。I/Oはread/write/cancelledの物理byte差分を別々に保存した。全対象の試行別CPU・I/O・RSS中央値と観測最大値は[comparison.json](comparison.json)に収録している。

## 全標本のhashと判定を再計算できる

Python標準ライブラリだけで次を実行する。製品の再実行や追加取得は不要。

```sh
python3 -B reports/alopex-v0.8.17-performance/run-42444773094/sqlite_public_report.py
```

制御commitは`164ef30c80518c3c14dc459fa63f6fa124bb335d`。原本artifactは`13603480576`、digestは`sha256:d5f194b427c6637dc15e8bbdca0b90aa5a3bf54256e8029bde3362787a6f2fee`。全24 workerのwait、投入資産・venv・fixture・復号一時ファイルの削除を確認した。終了後のmm統計消失3件は実終了をwaitで確認して末尾観測から除外し、生存中の欠測を0補完していない。暗号化原本・監査コードは保持している。
