# v0.8.17 CSV固定比較

34,250行のCSVでは、最初のbatch取得が修正前比38.71%、全batch取得が42.88%短縮した。一方、3行のplan・最初のbatch・全batch取得は既定基準で退行となった。大きい入力での改善を確認できたが、小さい入力の増加原因が未確定のため、CSV全体の性能受入は継続する。

[run 42439916597](https://github.com/alopex-db/alopex/actions/runs/42439916597)で24セルを逐次実行した。全1,512計測標本、warmup込み1,728観測区間について、資産、全値oracle、CPU・RSS・I/O、再計算、プロセス終了と回収を照合した。本報告はこの実行の全計測標本を収録する。

## 同じ入力と計時境界で4対象を比較した

公開版はPyPIのv0.8.16 wheelをそのまま使用した。修正前と候補は同じRust 1.96.0・maturin 1.14.1のrelease build。candidateは#811の製品修正を含む資産であり、正式配布資産の認定を意味しない。Polarsは1.43.2とruntime wheelを公式hashで固定した。source tree、製品・参照wheelのhash、構築runは[manifest.json](manifest.json)に記録している。

planは遅延実行計画の生成、collectは通常の実体化、streamはbatchサイズ8,192による全行取得を測る。planとcollectは元の観測関数を呼び、戻り値の破棄を含む計時境界を維持した。streamは元のconsumerのfirst/total時計を使用する。firstは最初のbatch、totalは全batch取得までで、closeを含む外側の時間は別の数値として保存した。

資源観測のcallback、raw保存、全値検証はlatencyの外に置いた。各セルの前後で全行の値・型・NULL・順序を独立oracleと照合し、各計測標本でも行数を照合した。資産の元receiptと導入済みファイルのhashを実行前後で検査した。

### 3行の試行間差は、同じ試行内の揺れより大きい

3行の全batch取得は、修正前・候補とも約90 µs台と約150 µs台に分かれた。各試行の中央値と、その21標本のMADは次のとおり。

| 対象 | trial 1 中央値 / MAD µs | trial 2 中央値 / MAD µs | trial 3 中央値 / MAD µs |
| --- | ---: | ---: | ---: |
| before | 94.595 / 0.932 | 93.424 / 0.791 | 154.567 / 0.942 |
| candidate | 147.347 / 1.713 | 91.420 / 0.802 | 148.295 / 0.972 |

同番号試行の候補/修正前は1.5577、0.9785、0.9594だった。2組が短縮しても、事前に定めた集約比1.5577の退行判定は変えない。各試行内のMADは約0.8〜1.7 µsで、試行間の約50〜60 µs差より小さい。単発の遅い標本だけが集約値を引き上げた形ではない。CPU時間にも同様の試行差があるが、その原因はこの観測だけでは決まらない。

3行planは2.265→2.395 µs、差0.130 µsで+5.74%となった。各試行の中央値は修正前2.354/2.265/2.244 µs、候補2.394/2.434/2.395 µs。3行collectは試行内でも速い標本と遅い標本が混在し、一部の試行でMADが大きい。全標本と区間別の分布は[comparison.json](comparison.json)から確認できる。

ソースを比較すると、DataFrame crateとPython DataFrame bindingの差分は`streaming_csv.rs`に限られる。plan生成と通常の`LazyFrame::collect()`は同一であり、通常collectはeager executor、batch取得はstreaming経路を使う。このため、plan・通常collectの増加をframerの処理変更へ直接帰属する根拠はない。製品全体の変更やプロセスごとの差を含む原因の切り分けが残る。ソースが同じことを、退行判定の取消理由にはしない。

## CPUとRSSは減少したが、メモリの純増量ではない

34,250行の全batch取得で、区間CPU中央値は4.998→2.859 ms、区間RSS最高値の中央値は45,334,528→44,974,080 bytesだった。plan・collectと3行のRSS中央値も修正前を下回った。

RSSは入力やimport済みmoduleを含むworker全体のkernel観測値である。区間ごとにhigh-waterをresetし、reset直後と終了時の最大値を採用した。rawにはreset前後・終了時の値と減少flagも保持する。kernel集計の精度に制限され、当該処理が追加したメモリ量や厳密なallocation peakとは一致しない。資源区間はcounter読取りの一部とstreamのcloseを含み、latencyの時計とは別に扱う。

I/Oはread/write/cancelledの物理byte差分を個別に保存した。各試行・区間の計測標本中央値はすべて0 bytesである。これは全標本やfixture生成・導入・結果保存を含むI/Oが0という主張ではない。全対象のCPU、I/O、RSS中央値・観測最大値はcomparison.jsonに残している。

## 全1,512標本から判定を再計算できる

Python標準ライブラリだけで、次のように検査できる。実行場所によらずスクリプトと同じディレクトリのデータを読む。

```sh
python3 -B reports/alopex-v0.8.17-performance/run-42439916597/csv_public_report.py
```

制御commitは`d3a1a85327f50c88a0819882cdae3ad8782dd702`。原本artifactは`13600788036`、digestは`sha256:5cab27b03531ea612d2a3f5aff7cc2cf4b68eae5df9875fe77ceec598748edf6`。暗号化原本、非公開receipt、監査コードを保持した。全24 workerのwaitと資産・venv・fixture・復号一時ファイルの削除を照合済み。終了後のmm統計消失3件はwaitで実終了を確認して末尾観測から除外し、生存中の欠測を0で補完していない。
