候補は修正前より検索時間が増えました。同じefの比較では32・64・128・256が退行、16はノイズ超過で保留です。検索精度は維持され、全75設定点の最小recallは0.9965でした。性能受入は未完了です。

## 条件と比較対象

9,171×128の正規化ベクトル、seed42、200 query、top10、M16、efConstruction200、ef16/32/64/128/256、3試行。各設定点は最低10,000検索かつ2秒です。全200 queryのwarmup、構築後の更新・削除・再挿入・reopenを元のハーネスどおり実行しました。

- 公開v0.8.16、修正前 `34ce28d5c15377837cb78b15a261cfa2c05757a8`、候補用 `2ea6befef45fe6019c6976cfd8260371b0a57bde` の既存release wheelを使用。候補 `337de47da1b04e5e47a39833775f0903b6f46584` と候補用資産の製品crate/Cargoは同一です。
- 修正前のvector core・HNSW cache・embedded/Python Database APIは#681修正前 `5e05f014` と一致します。共有グラフ等を含む変更群の比較であり、単一変更の因果効果とは扱いません。
- 参照はhnswlib 0.8.0とFaiss CPU 1.15.0。公式配布物をhash固定し、hnswlibは元ソースのコンパイラ設定で逐次構築しました。実際に導入したwheelのhashはmanifestに保存しています。
- 各試行を新しいworkerで逐次実行し、対象の順序を回転させました。同一run内で入力を共用し、入力hashを前後で照合しています。

主指標は各試行のquery p50を3試行で中央値にした値です。1検索の時計はPython searchとtop10 ID変換を含みます。elapsed/queryの平均、QPS、別観測のnative整数µsは別指標です。legacy residualは別々の観測の差であり、Pythonだけの所要時間ではありません。

事前基準は3×max(両対象の試行p50のMAD)≤修正前中央値の5%。時間比>1.05を退行とし、改善には時間比≤0.95・短縮量>3 MAD・全3組の短縮を要求します。ノイズ超過は保留とし、増加を消しません。

## CPU・RSS・I/Oと原因の切り分け

資源観測は元の検索関数全体を囲み、計時後のpercentile集計と観測処理の負担を含みます。索引構築、warmup、oracle、raw保存は区間外です。RSSはworker全体のkernel観測値であり、検索操作だけの割当量ではありません。

CPU/queryは各試行の(user CPU＋system CPU)を検索数で割り、3試行の中央値にしたものです。実行時間に下限があるため検索数は対象間で異なり、CPU合計だけでは効率を比較しません。全75区間のread_bytes・write_bytes・cancelled_write_bytesの差分は0でした。

修正前と候補は、5 ef×3試行×200 queryの各組でnodes_visitedとdistance_computationsがすべて一致しました。一方、別観測のnative時間も増えています。検索処理量の増加やPythonだけの負担に原因を限定する根拠はありません。ソース差分ではノード格納がVecからページ単位の共有構造へ変わっており、参照経路と局所性を次に調べます。現時点でこの変更を原因と断定しません。

## 公開データの再計算

```sh
python3 -B hnsw_public_report.py
```

manifest.jsonに元資産・入力・raw・監査コードのhashを保存しています。rawの75 gzipファイルには全個別時間、検索前後のtop10 ID、native観測と許可した資源カウンターを収録しました。truth.jsonは精度照合用のIDです。再計算コードは全rawのhash・点数・個別時間からのpercentile・recall・資源差分・同recall最速点を検査し、comparison.jsonとの一致を要求します。入力ベクトルのexact oracleは暗号化原本の独立監査で照合済みです。

#712の段階受入は検索退行の原因・対処、他対象の退行・ノイズ保留と資源増加の評価、最終候補資産への対応付けが残ります。#681の書込み改善と今回の検索退行は別に判定します。
